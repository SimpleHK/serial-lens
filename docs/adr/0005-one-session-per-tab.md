# One split-view pane per session: monitored ports and opened log files

The monitor view runs one session per split-view pane instead of a single shared controller. A **port session** owns its own `MonitorController` (so several ports stream simultaneously, side by side) and its own log-to-file state; a **file session** is a read-only snapshot of an opened `.log`/`.txt` file fed through the same append pipeline (cap included: only the newest `maxBufferLines` lines are kept). Every host→webview state/append/logging message carries a `sessionId`; the webview keeps per-pane buffers, virtualized renderers, scroll position, and Follow/Lock state. **Each pane is self-contained**: its header carries the port-local actions (start/stop, clear, log-to-file, export, follow/lock, find, close) and its bottom bar the port-local send input — only genuinely global display choices (tag filter mode, timestamps, log directory, tag management) stay in the top rows. A pane captures its serial settings at creation and restarts with them regardless of what the hardware row currently shows. ＋ or Start opens another monitor and the view splits wider (narrow viewports scroll horizontally). The public API maps onto the same sessions (`startMonitoringPort` opens one; its pane outlives `stopMonitoring` until closed, and several API monitors may run at once). Reconnecting over a stopped pane opens a new session that replaces the old pane only once it connects, so a failed open never destroys the previous buffer.

Find is a pane-local, editor-style widget (Ctrl+F or the pane's magnifier): match-case / whole-word / regex toggles, occurrence counter, prev/next navigation, and text-level match highlighting through the CSS Custom Highlight API — so highlights never touch the DOM text nodes and text selection (tag creation) keeps working. Occurrences are computed over the pane's *visible* lines in rendered-text coordinates, recomputed on query edits, appends, filter changes, and timestamp toggles.
